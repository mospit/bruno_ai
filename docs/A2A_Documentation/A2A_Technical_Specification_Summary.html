Agent2Agent (A2A) Protocol Technical Specification Summary

1. Protocol Overview

The Agent2Agent (A2A) Protocol is an open standard designed to facilitate communication and interoperability between independent, potentially opaque AI agent systems. The protocol enables agents to discover each other's capabilities, negotiate interaction modalities, manage collaborative tasks, and securely exchange information without requiring access to each other's internal state, memory, or tools.

1.1 Key Design Principles

  • Simple: Reuse existing, well-understood standards (HTTP, JSON-RPC 2.0, Server-Sent Events)
  • Enterprise Ready: Address authentication, authorization, security, privacy, tracing, and monitoring
  • Async First: Designed for potentially long-running tasks and human-in-the-loop interactions
  • Modality Agnostic: Support exchange of diverse content types including text, files, structured data
  • Opaque Execution: Agents collaborate based on declared capabilities without sharing internal implementations

2. Transport and Format Requirements

2.1 Transport Protocol

A2A communication must occur over HTTP(S). Production deployments must use HTTPS with modern TLS configurations (TLS 1.3+ recommended) and strong cipher suites.

2.2 Data Format

A2A uses JSON-RPC 2.0 as the payload format for all requests and responses. The Content-Type header for HTTP requests and responses containing JSON-RPC payloads must be application/json.

2.3 Streaming Transport

When streaming is used, the server responds with HTTP 200 OK status and Content-Type: text/event-stream. The response body contains Server-Sent Events (SSE) as defined by the W3C specification, with each SSE data field containing a complete JSON-RPC 2.0 Response object.

3. Security Requirements

3.1 Transport Security

Production deployments must use HTTPS. A2A Clients should verify the A2A Server's identity by validating its TLS certificate against trusted certificate authorities during the TLS handshake.

3.2 Authentication Process

  1. Discovery: Client discovers server's required authentication schemes via the authentication field in the AgentCard
  2. Credential Acquisition: Client obtains necessary credentials through out-of-band process specific to the required authentication scheme
  3. Credential Transmission: Client includes credentials in appropriate HTTP headers of every A2A request

3.3 Server Authentication Responsibilities

The A2A Server must authenticate every incoming request based on provided HTTP credentials and declared authentication requirements. Servers should use standard HTTP status codes (401 Unauthorized, 403 Forbidden) and include relevant HTTP headers with 401 responses.

3.4 Authorization

Once authenticated, the A2A Server is responsible for authorizing requests based on the authenticated client/user identity and its own policies. Authorization may be enforced based on specific skills requested, actions attempted, data access policies, or OAuth scopes.

4. Core Data Objects

4.1 AgentCard Object

The AgentCard is a JSON metadata document that describes an A2A Server's identity, capabilities, skills, service endpoint, and authentication requirements.

Field Name Type Required Description
protocolVersion string Yes Version of A2A protocol supported
name string Yes Human-readable name of the agent
description string Yes Human-readable description
url string Yes Base URL for agent's A2A service
capabilities AgentCapabilities Yes Optional A2A protocol features supported
securitySchemes object No Security scheme details for authentication
defaultInputModes string[] Yes Input media types accepted
defaultOutputModes string[] Yes Output media types produced
skills AgentSkill[] Yes Array of agent capabilities

4.2 Task Object

Represents the stateful unit of work being processed by the A2A Server. Tasks progress through defined lifecycle states and cannot be restarted once they reach a terminal state.

Field Name Type Required Description
id string Yes Server-generated unique task identifier
contextId string Yes Server-generated ID for contextual alignment
status TaskStatus Yes Current status of the task
artifacts Artifact[] No Array of outputs generated by the agent
history Message[] No Array of recent messages exchanged
metadata object No Arbitrary key-value metadata

4.3 Message Object

Represents a single turn of communication between a client and an agent, containing a role and one or more content parts.

Field Name Type Required Description
role string Yes Either "user" or "agent"
parts Part[] Yes Array of content parts
messageId string Yes Unique identifier for the message
contextId string No Context identifier for grouping
taskId string No Associated task identifier

4.4 Part Union Type

The fundamental unit of content within Messages and Artifacts. Three types are supported:

4.4.1 TextPart

  • kind: "text"
  • text: string content
  • metadata: optional additional information

4.4.2 FilePart

  • kind: "file"
  • file: FileWithBytes or FileWithUri
  • metadata: optional additional information

4.4.3 DataPart

  • kind: "data"
  • data: JSON object containing structured data
  • metadata: optional additional information

4.5 TaskStatus Object

Represents the current state and associated context of a Task.

Field Name Type Required Description
state TaskState Yes Current task state enum
message Message No Additional context message
timestamp string Yes ISO 8601 timestamp

4.6 TaskState Enum

Defines the possible states of a task:

  • submitted: Task has been received and queued
  • working: Task is actively being processed
  • input-required: Task requires additional input from client
  • completed: Task has been successfully completed
  • canceled: Task has been canceled
  • failed: Task has failed due to an error
  • rejected: Task was rejected by the agent
  • auth-required: Task requires additional authentication
  • unknown: Task state cannot be determined

5. API Methods

All API methods use HTTP POST with JSON-RPC 2.0 payloads, except for the authenticated extended card endpoint which uses HTTP GET.

5.1 message/send

Initiate or continue a task with a message. Returns either a Task object for ongoing tasks or a Message object for simple replies.

5.2 message/stream

Similar to message/send but opens a Server-Sent Event stream for real-time updates. Streams TaskStatusUpdateEvent and TaskArtifactUpdateEvent objects.

5.3 tasks/get

Query the current state and history of a task by ID. Used for polling-style interactions to check task completion.

5.4 tasks/cancel

Cancel a running task by ID. Returns the latest task state, ideally with state "canceled" but may fail if the task cannot be stopped.

5.5 tasks/pushNotificationConfig/set

Set or update webhook URL and authentication information for push notifications on a task.

5.6 tasks/pushNotificationConfig/get

Retrieve the current push notification configuration for a task by ID.

5.7 tasks/pushNotificationConfig/list

Enumerate all push notification configurations associated with a task.

5.8 tasks/pushNotificationConfig/delete

Remove a push notification configuration from a task.

5.9 tasks/resubscribe

Reconnect to the Server-Sent Event stream for a task after connection interruption.

5.10 agent/authenticatedExtendedCard

HTTP GET endpoint that provides a more detailed Agent Card after authentication, if the agent supports this capability.

6. Error Handling

A2A follows JSON-RPC 2.0 error format with standard and protocol-specific error codes:

6.1 Standard JSON-RPC Error Codes

  • -32700: Parse error
  • -32600: Invalid Request
  • -32601: Method not found
  • -32602: Invalid params
  • -32603: Internal error
  • -32000 to -32099: Server error range

6.2 A2A-Specific Error Codes

  • -32001: TaskNotFound
  • -32002: TaskNotCancelable
  • -32003: PushNotificationNotSupported
  • -32004: UnsupportedOperation
  • -32005: ContentTypeNotSupported
  • -32006: InvalidAgentResponse

7. Agent Discovery

A2A Servers must make an Agent Card available through discoverable endpoints. The recommended location for an agent's Agent Card is at the well-known URI: https://{server_domain}/.well-known/agent.json

7.1 Discovery Mechanisms

  • Well-Known URI: Accessing a predefined path on the agent's domain
  • Registries/Catalogs: Querying curated catalogs of agents
  • Direct Configuration: Pre-configured Agent Card URLs or content

7.2 Security Considerations

Agent Cards containing sensitive information must be protected by appropriate access controls. It is not recommended to include plaintext secrets directly in Agent Cards.

8. Supported Modalities

A2A supports multiple content types and interaction modalities:

8.1 Content Types

  • Text: Plain text content for conversational interactions
  • Structured JSON: Machine-readable data for forms and parameters
  • Files: Binary content transmitted by reference (URI) or as base64-encoded bytes
  • Mixed Content: Combinations of the above within single messages

8.2 Media Type Declaration

Agents declare supported input and output media types in their Agent Cards through defaultInputModes and defaultOutputModes fields. Individual skills may override these defaults with specific requirements.

9. Asynchronous and Streaming Features

9.1 Streaming Support

Agents may support Server-Sent Events for real-time task updates. This capability is declared in the Agent Card's capabilities.streaming field.

9.2 Push Notifications

For long-running tasks or scenarios where persistent connections are impractical, agents may support push notifications to client-provided webhook URLs. This capability is declared in the Agent Card's capabilities.pushNotifications field.

9.3 Task Lifecycle Management

Tasks progress through defined states and may involve multiple message exchanges. Clients can monitor task progress through polling, streaming, or push notifications depending on the agent's capabilities and the interaction requirements.

10. Implementation Requirements Summary

10.1 Mandatory Requirements

  • HTTPS transport for production deployments
  • JSON-RPC 2.0 payload format
  • Agent Card publication at discoverable endpoint
  • Authentication of all incoming requests
  • Support for core data objects (Task, Message, Part, etc.)
  • Implementation of basic API methods (message/send, tasks/get)

10.2 Optional Features

  • Server-Sent Events streaming support
  • Push notification capabilities
  • Extended authentication card support
  • Protocol extensions
  • Task state transition history

10.3 Security Best Practices

  • Use modern TLS configurations (TLS 1.3+ recommended)
  • Implement proper input validation and sanitization
  • Apply rate limiting and resource management
  • Follow principle of least privilege for authorization
  • Validate webhook endpoints for push notifications
  • Implement proper error handling and logging

11. Conclusion

The A2A Protocol provides a comprehensive framework for building interoperable AI agents. By adhering to these technical specifications, developers can create agents that seamlessly communicate and collaborate across different platforms and vendors. The protocol's emphasis on security, flexibility, and standards compliance ensures that A2A-compliant agents can operate effectively in enterprise environments while maintaining the scalability needed for complex multi-agent systems.

This technical specification serves as the authoritative reference for implementing A2A-compliant agents. For additional implementation guidance, sample code, and tutorials, developers should refer to the complete A2A documentation and SDK resources.
