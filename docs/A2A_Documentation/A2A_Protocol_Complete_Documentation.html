1. Introduction

The Agent2Agent (A2A) Protocol is an open standard designed to enable seamless communication and collaboration between AI agents. In a world where agents are built using diverse frameworks and by different vendors, A2A provides a common language, breaking down silos and fostering interoperability.

This comprehensive documentation covers the complete A2A protocol specification, including core concepts, implementation guidelines, and practical tutorials for building A2A-compliant agents.

2. What is A2A?

The Agent2Agent (A2A) Protocol is an open standard designed to solve a fundamental challenge in the rapidly evolving landscape of artificial intelligence: how do AI agents, built by different teams, using different technologies, and owned by different organizations, communicate and collaborate effectively?

As AI agents become more specialized and capable, the need for them to work together on complex tasks increases. Imagine a user asking their primary AI assistant to plan an international trip. This single request might involve coordinating the capabilities of several specialized agents:

  1. An agent for flight bookings
  2. Another agent for hotel reservations
  3. A third for local tour recommendations and bookings
  4. A fourth to handle currency conversion and travel advisories

Without a common communication protocol, integrating these diverse agents into a cohesive user experience is a significant engineering hurdle. Each integration would likely be a custom, point-to-point solution, making the system difficult to scale, maintain, and extend.

2.1 The A2A Solution

A2A provides a standardized way for these independent, often "opaque" (black-box) agentic systems to interact. It defines:

  • A common transport and format: JSON-RPC 2.0 over HTTP(S) for how messages are structured and transmitted
  • Discovery mechanisms (Agent Cards): How agents can advertise their capabilities and be found by other agents
  • Task management workflows: How collaborative tasks are initiated, progressed, and completed, including support for long-running tasks
  • Support for various data modalities: How agents exchange text, files, structured data, and other rich media
  • Core principles for security and asynchronicity: Guidelines for secure communication and handling tasks that involve human-in-the-loop processes

2.2 Key Design Principles

The development of A2A is guided by several core principles:

  • Simplicity: Leverage existing, well-understood standards like HTTP, JSON-RPC, and Server-Sent Events (SSE)
  • Enterprise Readiness: Address authentication, authorization, security, privacy, tracing, and monitoring from the outset
  • Asynchronous First: Support long-running tasks and scenarios where agents might not be continuously connected
  • Modality Agnostic: Allow agents to communicate using various content types beyond plain text
  • Opaque Execution: Enable collaboration without requiring agents to expose internal logic, memory, or proprietary tools

3. Key Concepts

The Agent2Agent (A2A) protocol is built around a set of core concepts that define how agents interact. Understanding these concepts is crucial for developing or integrating with A2A-compliant systems.

3.1 Core Actors

  • User: The end user (human or automated service) who initiates a request requiring agent assistance
  • A2A Client (Client Agent): An application, service, or AI agent that acts on behalf of the user to request actions from a remote agent
  • A2A Server (Remote Agent): An AI agent that exposes an HTTP endpoint implementing the A2A protocol, processes tasks, and returns results

3.2 Fundamental Communication Elements

3.2.1 Agent Card

A JSON metadata document that describes an A2A Server, including:

  • Agent identity (name, description)
  • Service endpoint URL
  • Supported A2A capabilities
  • Available skills
  • Authentication requirements

3.2.2 Task

A stateful unit of work that progresses through a defined lifecycle:

  • Each task has a unique ID defined by the agent
  • Tasks can be long-running or require multiple exchanges
  • States include: submitted, working, input-required, completed, failed

3.2.3 Message

A single unit of communication between client and agent:

  • Has a role (either "user" or "agent")
  • Contains one or more Part objects carrying content
  • Used for instructions, context, questions, and status updates

3.2.4 Part

The fundamental unit of content within Messages or Artifacts:

  • TextPart: Plain textual content
  • FilePart: File data (base64-encoded or URI-referenced)
  • DataPart: Structured JSON data

3.2.5 Artifact

Tangible outputs generated by the remote agent:

  • Examples: documents, images, spreadsheets, structured data
  • Composed of one or more Part objects
  • Can be streamed incrementally

3.3 Interaction Mechanisms

3.3.1 Request/Response (Polling)

Client sends a request and receives a response. For long-running tasks, the client periodically polls for updates until completion.

3.3.2 Streaming (Server-Sent Events)

For tasks producing incremental results or real-time updates. The server maintains an open HTTP connection and sends a stream of Server-Sent Events.

3.3.3 Push Notifications

For very long-running tasks where persistent connections are impractical. The server sends asynchronous notifications to a client-provided webhook URL.

4. Protocol Specification

4.1 Transport and Format

A2A communication occurs over HTTP(S) using JSON-RPC 2.0 as the payload format. Key requirements:

  • All communication MUST use HTTP(S)
  • Production deployments MUST use HTTPS
  • Content-Type header MUST be application/json
  • Streaming uses Server-Sent Events with text/event-stream

4.2 Security

A2A relies on established web security practices:

  • Transport Security: HTTPS with TLS 1.3+ recommended
  • Authentication: Credentials handled at HTTP transport layer
  • Authorization: Server-side policy enforcement based on authenticated identity
  • Identity Verification: TLS certificate validation against trusted CAs

4.3 Agent Discovery

Agents make their capabilities discoverable through Agent Cards:

  • Well-Known URI: https://{domain}/.well-known/agent.json
  • Registries: Curated catalogs of available agents
  • Direct Configuration: Pre-configured agent endpoints

4.4 Sample Agent Card Structure

{
  "protocolVersion": "0.2.5",
  "name": "Recipe Agent",
  "description": "Agent that helps users with recipes and cooking",
  "url": "https://recipe-agent.example.com/a2a/v1",
  "capabilities": {
    "streaming": true,
    "pushNotifications": false
  },
  "defaultInputModes": ["text/plain", "application/json"],
  "defaultOutputModes": ["text/plain", "application/json"],
  "skills": [
    {
      "id": "recipe-search",
      "name": "Recipe Search",
      "description": "Find recipes based on ingredients or cuisine",
      "tags": ["cooking", "recipes", "food"],
      "examples": [
        "Find me a recipe for chocolate cake",
        "What can I make with chicken and rice?"
      ]
    }
  ]
}

7. A2A and MCP: Complementary Protocols

A2A and the Model Context Protocol (MCP) are complementary standards for building robust agentic applications:

  • MCP (Model Context Protocol): Connects agents to tools, APIs, and resources with structured inputs/outputs
  • A2A (Agent2Agent Protocol): Facilitates dynamic, multimodal communication between different agents as peers

Together, they enable agents to access capabilities (via MCP) and collaborate with other agents (via A2A) to solve complex user requirements.
