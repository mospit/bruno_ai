Comprehensive Guide to Memory System Implementation for Bruno AI

This guide details the memory system for Bruno AI V3.1, focusing on state management, context persistence, caching, and related techniques to support collaborative tasks in grocery shopping, food management, and meal prep. Tailored to dependencies like FastA2A (for A2A protocol with Storage/Broker/Worker), PydanticAI (agent framework), Claude models (Sonnet 4 for reasoning, Haiku for efficiency), Redis/Postgres (data layer), and Instacart API (tools), it ensures efficient handling of user wants across sessions/agents (e.g., persisting "$200 Caribbean budget" contexts). Memory is crucial for multi-agent continuity without redundancy, targeting 20-40% token/cost savings and <1s latency.

The system uses short-term memory (in-session caching) for quick access, long-term (DB persistence) for user history, and agent-specific (A2A context_id) for collaboration. Builds on FastA2A's Storage for tasks/artifacts and PydanticAI's state handling.

1. Memory System Overview

  • Purpose: Maintain context (e.g., user preferences, task history) across A2A peer interactions and sessions, enabling adaptive collaboration without re-querying (e.g., recall pantry items in shopping flows).
  • Types:
    • Short-Term (Volatile): In-memory/RAM for current sessions (e.g., Claude context window: 200K for Sonnet 4).
    • Long-Term (Persistent): Redis/Postgres for cross-session recall (e.g., user wants history).
    • Agent-Specific: A2A context_id for shared state in multi-agent (e.g., Recipe Chef accesses Budget Analyst's cost data).
  • Challenges Addressed: Token bloat in Claude calls; data loss in distributed agents; consistency in user-driven iterations.
  • Dependencies Integration: FastA2A Storage/Broker for task persistence; PydanticAI state for agent internals; Redis for caching; Postgres for durable storage.

2. Key Components and Strategies

2.1 Context Persistence

Use FastA2A's context_id to link tasks/messages, ensuring continuity (e.g., maintain budget across agents).

  • Implementation: Generate context_id on first message; reuse for follow-ups. Store in Redis via FastA2A Storage.
  • Code Example (FastA2A with Redis):
from fasta2a import to_a2a, RedisStorage
from pydantic_ai import Agent
from redis import Redis

redis = Redis(host='localhost')
agent = Agent('anthropic:claude-4-sonnet', instructions='Persist user wants like budget')
app = to_a2a(agent, storage=RedisStorage(redis))  # Persists tasks/contexts in Redis

For multi-agent: Agents share context_id via A2A JSON-RPC (e.g., Pantry sends to Instacart: {"context_id": "abc123", "items": [...] }).

2.2 Caching Mechanisms

Cache repetitive data (e.g., Instacart prices, user preferences) to reduce Claude calls.

  • Redis for Hot Caching: Store short-term results (TTL 1hr) for fast hits (85% ratio target).
  • Postgres for Cold Storage: Durable user data (e.g., past sessions).
  • Implementation: Pre-check cache in PydanticAI wrappers; FastA2A Broker queues uncached tasks.
  • Code Example (Caching in PydanticAI with Redis):
import redis
from pydantic_ai import Agent

r = redis.Redis()
def cached_agent(agent):
    def wrapper(query, context_id):
        key = f"cache:{context_id}:{hash(query)}"
        if cached := r.get(key):
            return cached.decode()
        result = agent(query)
        r.set(key, result, ex=3600)  # 1hr TTL
        return result
pantry_agent = Agent('anthropic:claude-3.5-haiku', wrapper=cached_agent)

For Instacart: Cache API responses (e.g., prices) to avoid re-fetches in A2A loops.

2.3 State Management

  • Session State: PydanticAI's internal state for in-agent memory; share via A2A artifacts (e.g., JSON DataPart for budgets).
  • Task State: FastA2A persists tasks (status, history) in Storage; use Broker for scheduling (e.g., queue feedback iterations).
  • Implementation: Link to context_id; use Postgres for long-term (e.g., user wants DB).
  • Code Example (FastA2A Broker/Storage for State):
from fasta2a import Broker, RedisStorage

storage = RedisStorage(redis)
broker = Broker(storage=storage)  # Queues tasks for persistence
# In agent: broker.schedule(task) for async state updates

2.4 Compression and Optimization

Compress contexts to fit Claude limits (e.g., summarize histories with Haiku).

  • LLM Compression: Use Haiku to condense A2A messages.
  • Implementation: Pre-process in FastA2A Worker.
  • Code Example:
from anthropic import Client
from fasta2a import Worker

haiku_client = Client(model="claude-3.5-haiku")
class CompressedWorker(Worker):
    async def process(self, task):
        task.context = haiku_client.summarize(task.context, 
                                             "Compress keeping user wants like $200 budget")
        return await super().process(task)

3. Best Practices

  • Security: Encrypt sensitive data in Redis/Postgres; use A2A auth for state access.
  • Optimization: TTLs to avoid staleness (e.g., 5min for prices); Haiku for compression (50% token reduction).
  • Multi-Agent: Share minimal state via context_id; cache agent outputs.
  • Error Handling: Fallback to cached data on failures; log token usage.
  • Scalability: Redis clustering for high users; Postgres sharding for history.

4. Implementation Architecture

4.1 Memory Layer Structure

The memory system operates on multiple layers to ensure optimal performance and data persistence:

  • L1 Cache (Agent Memory): PydanticAI's internal state for immediate access within individual agents
  • L2 Cache (Redis): Distributed cache for inter-agent communication and session persistence
  • L3 Storage (Postgres): Long-term persistent storage for user profiles, historical data, and analytics

4.2 Context Sharing Protocol

Agents share context through standardized A2A messages with the following structure:

{
  "context_id": "unique_session_identifier",
  "agent_id": "source_agent_name",
  "timestamp": "ISO8601_timestamp",
  "data": {
    "type": "budget|inventory|preferences|history",
    "content": "serialized_data",
    "ttl": "time_to_live_seconds"
  }
}
